# Portfolio Website - Project Instructions

## Overview
Single-page personal portfolio for Parth Soni (Data Analyst). Fully hand-coded: pure HTML/CSS/JS, no framework, no build step. Live metrics (GitHub contribution graph, content-dashboard stats) are fetched at runtime; the graph is drawn by the vendored `github-activity.js` kit; webfonts are self-hosted.

## Tech Stack
- Vanilla HTML + CSS + JS - no framework, no build, no dependencies. `package.json` exists only to hold `node --test`; `functions/package.json` marks the Pages Functions as ES modules for Node without changing the module type of the browser scripts
- Fonts: self-hosted woff2 (Playfair, DM Sans) in `fonts/`
- Icons: inline `<svg class="icon">` (Font Awesome 6 free path data inlined, `aria-hidden` + `focusable="false"`) for buttons, connect tabs, social links. No icon CDN - the old Font Awesome stylesheet/webfonts were replaced by these SVGs
- Runtime APIs: GitHub REST (browser), this site's own `/api/contributions` and `/api/medium` Functions (the contribution calendar and the Medium feed, fetched server-side), and the Content Tracking Dashboard's own watchlist endpoint (dashboard metrics - see "The dashboard section" below)

## Agent surfaces (Markdown, llms.txt, privacy)
- `/` and `/privacy` answer `text/markdown` when the request names it (`Accept: text/markdown`) and HTML otherwise. Both HTML responses carry `Vary: Accept` and a `Link` to their Markdown alternate plus `/llms.txt`; `/index.md` and `/privacy.md` always answer Markdown. Unmatched paths stay 404, with a Markdown body when one is requested; a request that excludes both formats gets 406.
- The Markdown copy lives in `functions/_agent-docs.js`, **not** in a generator over `index.html`: the home page is an app shell whose GitHub, dashboard and Medium widgets fill in after hydration, so a DOM scrape would hand an agent the loading placeholders. Edit the copy there, then update the `Markdown home page` test if the facts change.
- `functions/_middleware.js` is the only place a request is rewritten. Adding a negotiated document means adding it to `DOCUMENTS` and `MARKDOWN_ALIASES`, linking it from `llms.txt` and the sitemap, and adding it to `tests/agent-readiness.test.mjs`. Do not add a second middleware with its own copy of the negotiation.
- `_routes.json` excludes static assets (CSS, JS, images, fonts) from the middleware, so a stylesheet or an image does not pay for a Function invocation. Keep `/`, `/privacy`, the `.md` aliases and the project pages out of its `exclude` list - a missing project URL still needs a negotiated 404.
- `llms.txt` follows the llmstxt.org shape (H1, blockquote summary, then sections) and its `## When to use this` section names the jobs the site is right for, how to call it, and what it is not (no API, no pricing, no booking). Generic marketing copy does not count as guidance here.
- `privacy.html` is a real page at `/privacy`, not a section of the home page: agents check a stable URL. It must stay true to the code - no cookies, one `sessionStorage` key, the GitHub and dashboard reads, the two same-origin API Functions, Cloudflare hosting and email.
- `node --test tests/*.test.mjs` (also in CI) imports the same middleware Pages runs, so a negotiation regression is caught without a deploy. `node tools/check-headers.mjs` and `node tools/build-projects.mjs --check` still cover the CSP copies and the generated project pages.

## Project pages (`projects/<slug>/`)
- One page per `#projects` panel at `/projects/<slug>/`. The brief's `/projects/:slug` contract is met by that form; the host 308s `/projects/<slug>` to the trailing-slash URL, which is why every link and the sitemap use the slash.
- They are **generated, not hand-written**: `node tools/build-projects.mjs` reads each panel's number, title, status badge, image, description, stack tags and links out of `index.html` and writes `projects/<slug>/index.html`. Change a panel, then run the tool - retyping a project into its page would be a second copy of the same content, free to drift, which is the failure the dashboard section was rewritten to remove.
- `node tools/build-projects.mjs --check` (CI, `.github/workflows/check.yml`) re-derives every page and fails on: a page that no longer matches its panel, a missing page, a project page whose CSP differs from `index.html`'s, a canonical that is not that page's own URL, a missing `sitemap.xml` entry, a link to a file that does not exist, or a panel with no slug. It also deletes a page whose panel has gone - so remove the panel first, then rebuild.
- Slugs are keyed by panel id in `SLUGS`. They are URLs, so they are never derived from a title; adding a project means adding its panel and one line there.
- The CSP `<meta>` is copied out of `index.html` at generation time, so the two cannot disagree, and `_headers`' `/*` block already covers these paths - there is no third policy to maintain. `style-src 'self'` still holds: the pages carry no inline style and no inline script.
- Asset URLs on these pages are root-absolute (`/style.css`, `/project-*.jpeg`). The pages sit two directories down, where the home page's relative paths would 404.
- `script.js` is included unchanged. Every home-only block is guarded by the element it needs, so the header shadow, mobile drawer and scroll state work here without a page-specific script.

## Code Style / Conventions
- Semantic class names; keep inline `style=""` out of new markup and add classes to `style.css`
- Icons: add `<svg class="icon" aria-hidden="true" focusable="false" viewBox="…"><path d="…"/></svg>` (copy `<path>` from Font Awesome 6 free SVGs). Icon spacing/size CSS lives at the bottom of `style.css` under "Inline icon SVGs" - `svg.icon`, `.footer-link svg.icon`, `.connect-tab svg.icon`, etc.
- CTA buttons get a leading/trailing arrow icon; social/connect links use brand icons (GitHub, LinkedIn, Medium, X, and `fa-chart-simple` for Tableau)

## The GitHub contribution grid
- It reads **this site's own `/api/contributions`** (the cache, the upstream and what it cannot fix are described above), and the picture is **the design system's `ActivityHeatmap`** (`github-activity.js` + `github-activity.css`), not markup written here. The same kit draws the grid on the other sites, so a second hand-rolled "year of squares" would be a copy free to drift - the one this replaced carried its own month-label arithmetic, its own five shades and its own total, none of which the portfolio owns.
- `script.js` keeps what is the portfolio's: the read and the failure line (`Contribution graph unavailable right now…`, never an empty box). Sizing is not its business - the kit measures whatever card it is given, picks the largest square that still fits 53 columns, and follows the card with a `ResizeObserver`. The kit's month row is a grid of the same cell size, so the labels follow that measurement instead of being positioned by hand, and a hidden connect tab waits for its first real width rather than needing a 0-width guard in this repo.
- Shading is by **quartile of the non-zero days**, not a fraction of the busiest one: a single release week would otherwise wash the other 364 days into one shade. The endpoint's own `level` is dropped for that reason - one grid, one scale.
- The grid is one `role="img"` carrying the year in its label, and the footer (total + five busiest weeks) is a real `<ol>` outside it, so nobody has to walk 365 squares. Each square keeps a `title` with its date and count.
- `github-activity.js` loads **before** `script.js` and is **not** deferred, like `glide-select.js`: the parser reaches `script.js` first, so the kit has to be defined by then. The CSS is mapped, not restyled - `style.css` sets the five `--ga-*` shades to the card's orange ladder.

## The dashboard section (`#dashboard`)
- It reads **the Content Tracking Dashboard's own store**: `https://contenttrackerdashboard.pages.dev/.netlify/functions/watchlist`, the rows that dashboard's SPA renders off its D1 watchlist. It deliberately does **not** read the dashboard's Google Sheet, which is what it used to do - the Sheet stopped being that store when the dashboard moved to D1, so the two were copies free to drift, and they did (a title saved without a year was counted here and not there). Reading the store is what makes them agree by construction.
- That host is in `connect-src` in **both** CSP copies (the `<meta>` tag and `_headers`) and is pinned by `tools/check-headers.mjs`. The dashboard's `netlify/functions/watchlist.js` answers this origin and no other through an origin-scoped CORS allowance (`ALLOWED_ORIGINS`, plus `localhost` on any port for local dev). If this site ever moves host, that list needs the new origin - otherwise the section silently falls back to its snapshot instead of failing loudly.
- Figures are never typed into the markup. The four KPI cards and the header count are written by `script.js` from the rows it read (`&hellip;` until then), and the shaping that turns rows into periods, genres and series lives once, in `dash-aggregate.js`.
- When the read fails, the section renders an embedded snapshot from `script.js` and says so in `.dash-snapshot-note` above the figures - a stale snapshot that reads as live is the disagreement this section exists to remove, so it is never silent.
- Refresh the snapshot after the store has moved on: `node tools/snapshot-dashboard-fallback.mjs` (`--check` reports staleness and writes nothing). It fetches the same endpoint and runs the same `buildLive()`, so the snapshot can drift in time but never in method. Never hand-edit the `SNAPSHOT:START/END` block.
- **It is refreshed on a schedule now** - `.github/workflows/refresh-snapshots.yml`, Mondays at 06:00 UTC, committing only when the figures have moved. Added 16 Oct 2026, after this snapshot was found committed on 13 Oct while the store had already moved on (386 titles / 3,048 hours, against the 388/3,047 the block recorded): the tool and its `--check` both existed, and nothing called them, which is the failure the workflow removes.

## The two Pages Functions (`functions/api/`)
- Both exist for the same reason: the runtime reads this site needs were being rented from third-party hosts, and a rented read is one nobody here can fix. `/api/medium` and `/api/contributions` answer on this origin, so **no third-party host is in `connect-src`** any more - what is left there is `api.github.com` and the dashboard's own endpoint, both of which the browser must reach directly.
- They are Pages Functions, not a Worker script: file-based routing means `functions/api/medium.js` is exactly the route `/api/medium`. Pages compiles `functions/` **from the repository root** at deploy time even though the published directory is the staged `.pages-dist` (proved in production by RBI's `/data/*` routes, whose layout is the same) - so a push that edits only a Function still deploys it, and `.assetsignore` keeps the sources from being uploaded and served as files.
- Each one caches in the colo cache explicitly (`caches.default`, `waitUntil`) under the TTL in its own response: 10 minutes for the feed, 12 hours for the calendar. A Function's response is not edge-cached by the platform, and `Cache-Control: no-store` is both wrong here and the one value the Cache API refuses to store.
- Verify them locally the way production wires them: `node tools/deploy-pages.mjs --assets . --out .pages-dist` then `wrangler pages dev .pages-dist`. A cold `/api/medium` takes ~0.4 s and a warm one ~0.008 s; that gap is the cache.

## The Medium callout ("Writing on Medium")
- It lists the **three newest** Medium articles, read on every load from **this site's own `/api/medium`** (`functions/api/medium.js`), which asks `https://medium.com/feed/@soni.soni.parth` server-side - where neither CORS nor the browser challenge applies - parses it with `medium-feed.js`'s `parseFeed()` and caches it for 10 minutes.
- It used to read `api.rss2json.com`, a free third-party JSON proxy. On **15 Oct 2026 that proxy answered HTTP 500 `{"status":"error","message":"Internal error"}` while Medium's feed itself was returning 200 with 10 items**, so the callout rendered nothing for every visitor and nothing in the page could fix it. That is the failure this Function removes: it is the third-party runtime dependency that broke, not the feed.
- It used to show **two hand-typed** articles from a previous race weekend whenever the read failed, and said nothing, so the callout sat on September titles looking current for weeks. It now lists three, and the three are chosen by `medium-feed.js` rather than inside the section: `latestPosts()` filters, sorts on `pubDate` (never trusting the proxy's order), and labels them once for both the page and the snapshot tool.
- The list is served with a snapshot baked into `index.html` between the `MEDIUM:START/END` markers (never hand-edit that block). When the live read fails the list stays and a visible note below it (`.medium-snapshot-note`, hidden in the markup until then) says these are the newest articles as of `data-taken` - the card is never empty, and a snapshot is never passed off as live.
- Refresh the snapshot after publishing: `node tools/snapshot-medium-fallback.mjs` (`--check` reports staleness and writes nothing, exit 1). It reads the same URL and runs the same `latestPosts()`, so the snapshot can drift in time but never in method.
- The weekly `refresh-snapshots` workflow refreshes it too, behind a `--check` that fails the run rather than committing a snapshot the tool itself rejects. An article published between runs is worth pressing **Run workflow** for: the list goes stale on publish, not on a schedule.

## Build & Run
- No build step. Serve the folder with any static server (`python -m http.server`) and open `index.html`. Font Awesome + runtime APIs require network.

## Deploy
- The site is **one Cloudflare Pages project** named `parth-portfolio-wb` (`parth-portfolio-wb.pages.dev`), and that address is the only one: every link and self-reference in the repo names it - the manifest, sitemap and robots here, and the portfolio links in the portal and UCD. The static-assets-only Worker that used to mirror it (a second hostname, `portfolio.parth10.workers.dev`, that nothing pointed at) is deleted, and with it the config that could have republished it: there is no worker script here, so a push is a Pages build and nothing else.
- There is no `wrangler.toml` either, and none is needed: the project is configured in the Pages dashboard (production branch `main`, build command `node tools/deploy-pages.mjs --assets . --out .pages-dist`), and `functions/` is compiled from the repository root without being named anywhere.
- A push to `main` publishes it: the project is connected to this repository - **Cloudflare Pages**, production branch `main`, preview builds off, build command `node tools/deploy-pages.mjs --assets . --out .pages-dist`, output directory `.pages-dist`. `_headers` is kept for Pages to read from the staged copy while every other ignored file is left out, and a `404.html` is generated so an unknown path is a 404 rather than the home page. `Misc/pages-deploy.sh portfolio` uploads that same staged directory by hand and is the fallback path, not the only one.
- `.assetsignore` is what keeps `tools/`, the docs, `.git` and the config files out of the upload - a file that is never uploaded cannot be served, which is stronger than the 404 rules this site used to rely on.
